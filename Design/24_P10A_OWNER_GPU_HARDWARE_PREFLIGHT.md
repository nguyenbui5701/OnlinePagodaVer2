## 3. Acceptance thresholds are targets, NOT automatically PASS

- **Target** from Design 10 is **~30 FPS sustained** at 720×1280 during normal camera and real gift focus; treat an actual mean below 30, frequent p95 frame >33.3ms, severe ≥250ms spikes, browser crashes/context losses or unstable VRAM as FAIL/PARTIAL with a per-device breakdown, not as a hidden “nominal 30 FPS” claim. p95 ≤33.3ms is a *strict desired* 30 FPS smoothness criterion; if browser display caps or workload makes it unattainable, report the actual outcome and a proposed cap/quality tradeoff rather than retroactively lowering measured results.
- **Never force 30 FPS by artificially sleeping/dropping frame samples** and then call it stable. Record native Hz and whether browser throttles; measure correct actual wall time. Distinguish tab in background, rendering hidden, virtual engine time and real elapsed time.
- GPU memory, driver/device names and VRAM detection must be **actual observable samples**, and user can provide them manually. JS heap is not physical VRAM. 0/3/12/24 crowd targets in old Design 10 remain **design proposals**; only supported 3/12 visual occupancy can be benchmarked in this version without new code scope.
- Classify separately `P10A_ECO_3050TI_GPU_PASS|PARTIAL|HOLD`, `P10A_QUALITY_3060_GPU_PASS|PARTIAL|HOLD`, `P10A_30MIN_STABILITY_PASS|HOLD`, `P10A_HARDWARE_EVIDENCE_PENDING`, and `P10A_LIVE_STUDIO_NOT_AUTHORIZED`; no single global PASS if a machine is missing.
- If bottleneck: after collecting at least one real baseline, propose the **smallest reasoned** profile adjustment or batching/LOD change on a NEW Codex scope; do not downgrade visuals before observation or silently rewrite approved R16/P02/P05f/P07b1/flower material colors, alter gift semantics or drop existing real seats.
