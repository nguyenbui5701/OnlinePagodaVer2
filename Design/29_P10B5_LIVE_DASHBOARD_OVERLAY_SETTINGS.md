## 2. User workflow and UI
Use existing Vite preview port 5189 with real built entry points /dashboard/ and /overlay/ (exact direct navigation and refresh must work; correct asset base paths). Gateway port 5203 stays local. No new frameworks or ports required.
Dashboard works before any TikTok room is LIVE. Vietnamese UI: username, Connect/Disconnect, provider status/reason, overlay ready/applied revision, counters (Chat/Member/Like/Gift final/progress/viewers, distinguish packets from gift quantity), delivery uncertainty, settings, Save/Apply, Open Overlay link. No 3D rendering, audio output, gift simulation or ACK in dashboard.
Overlay is a clean 720x1280 portrait window with only approved scene/nameplates/chat/gift visuals; no settings, connection form, diagnostic text, or debug UI in captured surface. Off-line it shows the normal empty/decorative cinematic, no invented users or gifts. Keep a diagnostic report accessible to test tooling; errors/loading should be clear without leaking controls. Open a separate window via ordinary user click, not autoplay/popup automation.
Workflow: start two existing processes -> Dashboard configure/save -> open Overlay and wait for readiness -> Studio capture preview -> Owner starts authorized TikTok LIVE -> Dashboard Connect -> operate from Dashboard. Operator may disconnect separately from Studio. No automatic public broadcast.

## 3. Minimal runtime architecture
Keep packages/v2-live-gateway as local state/settings authority, existing connector and worker. Separate small dashboard entry and overlay entry in apps/v2-viewer; extract UI-free receiver from existing live-controls. Use existing local HTTP transport (no need for WebSocket, new DB or a new package). Retain old root query-based DEMO, evidence/inspect and PR23 legacy LIVE route for compatibility; old and new LIVE receivers must share the single-owner rule, never compete. Clearly link to new workflow.
- Explicit Overlay attach/heartbeat when scene ready, even offline; auto client ID is receiver correlation only. Exactly one receiver may claim lease; a second overlay cannot consume/reset active cursor. Dashboard status/settings/control must never acquire receiver lease, drain entries or ACK. Control Connect targets current ready receiver, not dashboard client ID; no receiver -> clear NOT_READY response, no worker launch. Disconnect keeps final queue drainable. Dashboard reload/close must never call closing disconnect, stop worker or reset room/counters. Overlay reload/close/lease loss keeps existing stop + uncertainty semantics: no silent gift loss or promised continuity; reopen and explicitly reconnect after previous session settles, no automatic gift replay. RAM-only transport unchanged.
- Preserve /poll consumed contiguous ACK, 48 batch limit, retransmission dedup, 256 bounded queue, final priority and sticky failures/closing uncertainty from R2. Preserve worker/mapper, roomEpoch/connection semantics, three authoritative seats, gift FIFO and camera returns. Separate lightweight status/config read (no event entries); dashboard poll e.g. 2s, overlay 250ms, avoid exhausting existing 350/min global budget (consider settings batching and bounded role-specific budgets if needed; do not remove rate limits).
- Token-free trusted local model from Design26 §10: exact loopback/Host/Origin/CORS, bounded JSON/schema/routes, no LAN/public exposure. No operator token. Local processes remain trusted, not authenticated. Do not expose provider credentials/raw viewer data or persist event history.

## 4. Settings contract
Single server-owned versioned settings.json under gitignored local data directory. Validate allowlisted keys/types/enums and ranges; reject unknown keys; safe defaults on missing/corrupt file with warning; atomic temp+rename, persist only successfully validated configuration, report write failures, don't falsely report saved/applied. No secrets or user event data. Distinguish saved/desired vs applied revision (Overlay reports its actual state); refresh Dashboard and reopen Overlay from saved settings. Username preference optional local only. Default Full Option ECO matches PR23 URL: profile eco, seed 9, look twilight, tree r17b, botanicals/diversity/presence/chatbubbles/gifticons/blessing on, ambience rich, seats rings, shots hero, fx on; clean portrait inherent. Use existing parsers/enum choices; verify each setting maps to actual renderer rather than invent options. Legacy query options unaffected.
- Startup/reload settings: profile, tree, seed, look, botanicals, diversity, seats, ambience, shots, fx/presence/chatbubbles/gifticons/blessing if currently initialization-bound. Save offline, apply to Overlay at next initialization or explicit controlled offline Apply/Reload. No hidden reload or live scene reconstruction. While connected, reconnecting or finals pending, save as pending for next safe start; never drop queue to apply settings.
- Hot settings: only existing or minimally safe presentation toggles proven to update without resetting renderer/Engine/camera or violating persistent nameplate/gift invariants. Expose live toggles only when actually wired and tested; otherwise clearly label restart/offline apply. No new camera timing controls or changes to gift priority. Dashboard may group camera/scene settings by existing options (hero route vs default), no unsupported UI pretending to work.
- Audio group can show LIVE muted/not yet available and future settings clearly disabled. PR22 DEMO and voice worker unchanged. LIVE audio integration including autoplay/one output owner and real-name TTS is next task, not this task.
- UI should distinguish offline source, provider connected/no events, verified events, degraded, local server absent, overlay not ready, pending settings. No fabricated counts. Actual gift final vs progress and confirmed Engine quantities remain distinct.
